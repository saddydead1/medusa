# Medusa — внутренняя документация

Это файл для разработчика и кодирующих агентов: архитектура, границы модулей,
переменные окружения, API, проверки и тесты. Пользовательская документация — в
`README.md`; сюда её не переносим, а отсюда не копируем.

Панель управления VPN-нодами: FastAPI + SQLite + статический фронт (vanilla JS).

## Запуск

```bash
uv sync
uv run medusa-panel                    # панель: http://127.0.0.1:8000
uv run medusa-node                     # нода: её API на http://127.0.0.1:9443

# прод-вариант панели
.venv/bin/python -m uvicorn src.panel.main:app --host 0.0.0.0 --port 8000
# нода без скрипта
.venv/bin/python -m uvicorn src.node.main:app --host 0.0.0.0 --port 9443
```

При старте панели создаётся база и в ней схема, строка настроек и первый владелец.
Пароль владельца при первом запуске генерируется и печатается в лог — его можно
задать самому через `MEDUSA_ADMIN_PASSWORD`.

### Панель

| Переменная | По умолчанию | Что делает |
| --- | --- | --- |
| `MEDUSA_DB` | `data/medusa.db` | путь к SQLite (WAL, `PRAGMA foreign_keys = ON`) |
| `MEDUSA_ADMIN_USER` / `MEDUSA_ADMIN_PASSWORD` | `admin` / случайный | владелец, создаётся при первом запуске |
| `MEDUSA_DEMO` | выключено | `1` — наполнить базу демонстрационными данными |
| `MEDUSA_AUTH` | **включено** | `0` — открыть API без учётки: только для разработки на своей машине |
| `MEDUSA_PANEL_BASE` | берётся из запроса | публичный адрес панели (`https://panel.example.com`): нужен за обратным прокси и для FIDO2 |
| `MEDUSA_PANEL_HOST` / `MEDUSA_PANEL_PORT` | `127.0.0.1` / `8000` | адрес и порт панели; флаг `--host`/`--port` перекрывает окружение, а в образе панели стоит `MEDUSA_PANEL_HOST=0.0.0.0`, `MEDUSA_PANEL_PORT=8000` (CMD их не зацикливает — порт правится одной строкой в compose) |
| `MEDUSA_NODE_AUTO` | `1` | `0` — выключить фоновый опрос нод (останется только кнопка «Проверить связь») |

### Нода

| Переменная | По умолчанию | Что делает |
| --- | --- | --- |
| `MEDUSA_NODE_HOST` / `MEDUSA_NODE_PORT` | `0.0.0.0` / `9443` | адрес и порт API ноды — отдельный от клиентских портов Xray |
| `MEDUSA_NODE_STATE` | `data/node/state.json` | файл состояния ноды (её API-ключ, ревизии), права 0600 |
| `MEDUSA_NODE_API_KEY` | — | готовый API-ключ вместо генерируемого; перебивает состояние |
| `MEDUSA_XRAY_BIN` | `xray` из `PATH` | путь к Xray; если его нет — нода честно говорит `xrayVersion: null` |

Фронт по умолчанию работает на живом API. Тестовый режим (мок прямо во фронтенде,
`USE_MOCK`) включается приставкой `?mock=1` в адресе страницы — удобно, когда бэкенда
нет под рукой.

Метрики читаются из `/proc` и `statvfs`, база — из стандартного `sqlite3`, схема заводится
SQL-скриптом, без ORM. `httpx` уже лежит в `fastapi[standard]` — им панель ходит к ноде.
Для socks5-прокси (связь панели с нодой за NAT) добавлен `socksio` (чистый Python; его же
использует httpx для SOCKS — своей реализации прокси у панели нет).
Для FIDO2 добавлены `cryptography` (проверять подписи ES256/EdDSA и сертификаты аттестата)
и `cbor2` (разбирать COSE-ключ и аттестат): своей реализации WebAuthn у панели нет.
Для QR страницы подписки добавлен `segno` (чистый Python, рисует SVG без картинок
и без Pillow).

## База

`src/panel/db.py` — схема и соединение (отдельное на каждый запрос):

`admins`, `sessions`, `settings`, `users`, `nodes`, `hosts`, `chains`.

Связки держатся на внешних ключах: удаление ноды уносит её хосты, удаление цепочки
уносит её хост. Хопы цепочки лежат в колонке `hops` как JSON — отдельной таблицы для
них нет.

## Эндпоинты

| Эндпоинт | Тело / что делает |
| --- | --- |
| `GET /api/meta` | имя и версия панели из `pyproject.toml` (`src/panel/meta.py`) |
| `GET /api/system` | метрики сервера: ЦП, ОЗУ, диски, uptime, hostname (`src/panel/system.py`) |
| `GET /sub/<токен>` | одно адрес на несколько применений: браузеру — страница, Clash — YAML `proxies:`, прочим — base64 ссылок всех хостов (`?raw=1` — без base64) |
| `GET /sub/<токен>/links` | явный путь со ссылками, всегда base64, без переговоров по Accept |
| `GET /sub/<токен>/qr/subscribe`, `GET /sub/<токен>/qr/host/<id>` | QR (SVG) на ссылку подписки и на ссылку одного хоста |
| `POST /api/login` | `{username, password}` → `{token, admin}`; `POST /api/logout`, `GET /api/me` |
| `GET/POST /api/users` | `{name, client?}`; `PATCH /api/users/{id}` `{status\|client\|name}`, `DELETE /api/users/{id}` |
| `POST /api/nodes` | `{name, address, apiKey, apiPort?, xray?, proxy?}` — без API-ключа ноду не создать (`422`); `GET` — список (ключ только masked + отпечаток, прокси — без пароля) |
| `PATCH /api/nodes/{id}` | `{address\|apiPort\|apiKey\|online\|xray\|proxy}`; `DELETE` |
| `GET /api/nodes/{id}/key` | настоящий API-ключ ноды: один на то, чтобы перенести его на саму ноду |
| `GET /api/nodes/{id}/proxy` | socks5-прокси этой ноды целиком, с паролем: нужен окну правки (в списках он masked) |
| `POST /api/nodes/{id}/check` | панель стучится на ноду: витрина без ключа, потом `/node/identity` с ключом, затем `/node/status` — его отчёт (трафик, ревизии, версии) ложится в базу; в ответе есть `traffic: {bytes, labels, at, error}` |
| `GET/POST /api/hosts` | `{name, node, protocol, network, security, port, address?}` + поля защиты и транспорта (ниже); в списке — обычные хосты и **входы** цепочек, промежуточные хопа скрыты; `DELETE /api/hosts/{id}` |
| `PATCH /api/hosts/{id}` | частичная правка всего, что видно в списке; хост цепочки — `409` («меняется вместе с цепочкой») |
| `GET/POST/PATCH /api/chains` | `{name, hops:[{node,protocol,network,security,port,address?,dest,serverNames,sni,rejectUnknownSni,fp,path,hostHeader,serviceName,grpcAuthority}]}` — PATCH правит цепочку целиком и пересобирает её хопа; `DELETE` снимает хопа на всех нодах |
| `GET/PATCH /api/settings` | одна строка настроек панели |
| `GET/POST /api/admins` | `{username, password}` (новая учётка всегда администратор); `PATCH` `{status\|password}`, `DELETE` |
| `GET/POST/DELETE /api/admins/{id}/keys` | аппаратные ключи учётки; `POST /api/admins/{id}/keys/begin` — вызов записи ключа |
| `POST /api/fido/begin`, `POST /api/fido/login` | вход по аппаратному ключу: вызов → ответ аппарата → сессия |

Панель работает под учёткой: сессия (`Authorization: Bearer …`) нужна на всех `/api`,
кроме `POST /api/login`, `POST /api/fido/*`, `GET /api/meta` и статики. До входа панель
показывает только окно входа.

Правила, которые держит бэкенд (а не фронт):

* права (подробности в разделе «Учётки, роли и сессии»): администратор — правка панели,
  но не чужих учёток; владелец защищён от изменений;

* порт на ноде занят — `409`, валидация тела — `422`, несуществующая запись — `404`,
  бессмысленная комбинация (`reality` поверх `ws`) — `400` с человеческим текстом на русском;
* хопы цепочки не могут попадать на одну и ту же ноду подряд, а хост цепочки нельзя
  удалить отдельно — только вместе с цепочкой.

## Конфиг Xray и применение его на ноду

Панель переводит свои таблицы в конфиг Xray (`src/core/xray_config.py` — чистый
рендер без БД и сети), нода его исполняет (`src/node/runner.py`):

* **адрес хоста ≠ адрес ноды.** У ноды адрес для связи панели с ней. У хоста — свой
  `address`, к нему подключается подписчик; пусто — значит к адресу ноды. Он же
  попадает в ссылки подписки (`vless://`, `vmess://`, `trojan://`, `ss://`) и в reality
  `serverNames`;
* инбаунды: прямой хост ноды = инбаунд, и каждый хоп цепочки = инбаунд своей ноды
  (см. раздел «Цепочки: переход трафика между нодами»). Поднятые протоколы: `vless`, `vmess`, `trojan`
  и `shadowsocks` (`SUPPORTED_PROTOCOLS`); hy2 хостом быть не может (`400` — панель
  не заводит хост, который не поднимется, а не «недописанный» хост). vmess всегда с
  `alterId: 0` и шифром `auto` (согласуемым), ss — `settings.users` с `method` у каждого
  подписчика (Xray различает людей именно по паре метод+пароль внутри одного инбаунда);
* **пароль shadowsocks — свой на каждый хост** (`ss_password(token, host.id)`): пароль ss
  и есть ключ шифрования конкретного порта, на другом порту он обязан быть другим.
  Пароль trojan, наоборот, один на все хосты (иначе подключённого человека пришлось бы
  переподписывать); vmess и vless узнают человека по `uuid5` от токена;
* пользователь в конфиге выводится из его токена подписки детерминированно:
  `uuid5` для vless/vmess (и для reality-подписчиков: Xray 26 узнаёт их по uuid,
  а различает внутри инбаунда по короткому id), пароль — для trojan. Один и тот
  же человек получает один и тот же id между рендерами; отключённый — исчезает;
* reality-хост при создании получает пару x25519 (панель, base64url как у
  `xray x25519`): приватный ключ едет в конфиг ноде, публичный — в ссылку
  подписки (`pbk=...`); наружу панель отдаёт только публичный. Xray 26 требует
  у серверного reality `dest` — адрес, которым нода «притворяется», когда
  рукопожатие не прошло; панель подставляет маскированный (`www.microsoft.com:443`);
* **в reality клиент называет сайт-маску, а не адрес ноды.** `serverNames` по умолчанию
  равен домену `dest`, и одно же имя едет во всё сразу: в `realitySettings.serverNames`
  конфига, в `sni=` ссылки подписки и в `servername`/`sni` Clash YAML. Наружу от такого
  хоста уходит настоящий сертификат сайта-маски, и строгие клиенты (Mihomo/Clash) сверяют
  sni именно с ним, а не с адресом ноды — иначе «certificate is valid for
  www.microsoft.com, not localhost». Поэтому адресом reality-хоста может быть и IP;
  панель отвергает только reality, прячущийся за IP (`dest`/`serverNames` обязаны
  содержать домен, `400`);
* `realitySettings.minClientVer` рендер не ставит, и это не косметика. В reality версия
  клиента — первые три байта session id в ClientHello, чистая формальность: клиенты
  семейства Clash пишут туда «1.8.2» (столько весит формат их ссылок), и порог вроде
  `24.0.0` просто отцепил бы весь Clash от ноды, ничего не прибавив к защите.
* **отдельные настройки защиты в окне хоста**: у выбранной защиты появляются её поля —
  у reality это маскированный адрес (`dest`, по умолчанию `www.microsoft.com:443`)
  и список принимаемых sni (`serverNames` через запятую, по умолчанию — домен маскировки);
  у tls — `sni` (он же имя, под которое нода выпустит сертификат, и он же `sni=`
  в ссылке подписки) и свои сертификаты (`certFile`/`keyFile` — всегда парой,
  иначе `400`; расширения `.crt/.pem/.cer` и `.key/.pem`; пусто — self-signed сама
  нода) плюс «отвергать чужой SNI». Панель принципиально не управляет alpn,
  версиями tls, наборами шифров и версиями клиента reality (никакого порога версии
  клиенту панель не ставит — см. замечание про `minClientVer` выше): у Xray свои
  разумные договорённости, ломать их пользовательской волей незачем.
  Пустое значение = разумное по умолчанию; поле чужой защиты панель отвергает
  (`400`: случайный sni у reality — это путаница, а не «лишнее»); при «none»
  показывать нечего и настраивать нечего, и именно «none» стоит по умолчанию
  в окне хоста — дырка включается только по явному выбору;
* **«Настройки транспорта»** (свёрнутый `<details class="adv">` в том же окне):
  у ws — путь (`path`) и Host-заголовок (`hostHeader`), у grpc — имя сервиса
  (`serviceName`) и authority (`grpcAuthority`); а ещё здесь живёт отпечаток
  клиента `fp` (utls: chrome/edge/safari/firefox/android/ios) — общее поле любой
  шифрующей защиты: оно уходит в `streamSettings.fingerprint` и в ссылку подписки
  `fp=...`, а при «none» его нет и отправить нельзя (`400`: без шифрования
  отпечатывать нечего). У tcp без защиты блок не появляется вовсе. Те же
  правила: поле чужого транспорта — `400`; пустая строка при правке — сброс к
  умолчанию; в конфиг и в ссылку подписки (`path=`, `host=`, `serviceName=`) поля
  едут, только если заданы;
* **правка цепочки**: кнопка «Изменить» на карточке цепочки открывает тот же диалог хопов,
  но предзаполненным (`openChain`/`openChainEdit`), и сохраняет через `PATCH /api/chains/{id}`
  — вместе с хопами. Свои порты правкой не считаются (перестановка хопов внутри тех же портов
  — не «порт занят»); диалог остаётся тем же, что и при создании, поэтому опции защиты
  фильтруются по протоколу точно так же;
* **правка хоста**: кнопка «Изменить» в списке открывает тот же диалог, что и создание,
  но предзаполненным (`openHostEdit`, `PATCH /api/hosts/{id}`); свой порт при правке
  не считается конфликтом, хост может переехать на другую ноду (грязными станут обе),
  а хост цепочки правится только вместе с цепочкой (`409`);
* tls-хостам нода выпускает self-signed сертификат сама (`cryptography`, на sni
  хоста — иначе на его адрес, 10 лет, каталог `<состояние ноды>/xray/certs`,
  закрытый ключ 0600); свои файлы (`certFile`/`keyFile`) панель передаёт как есть,
  подсказка генерации для такого хоста нода не посылается.
  Своей CA у панели нет. Xray 26 выбросил `allowInsecure`: клиенту называют
  отпечаток сертификата — `pinnedPeerCertSha256` (SHA-256 от DER; считается,
  например: `openssl x509 -in host-3.crt -outform DER | sha256sum`). Там, где
  клиент строгий или ленивый, лучше reality: он вообще без сертификатов.
  Пути к сертификатам нода записывает абсолютными: Xray почему-то ищет
  относительные файлы не рядом с конфигом, а рядом со своим бинарником;
* применение: правка хостов/пользователей помечает ноду грязной
  (`nodes.config_dirty`) и конфиг уезжает сам, в фоновом потоке, сразу после
  правки; опрос нод — страховка: не доставилось сейчас, доставится при первой
  же успешной связи. Если после всех правок конфиг вышел тем же, что уже
  применён (отпечаток `config_hash`), нода не дёргается вовсе. Каждая настоящая
  отправка поднимает `config_rev`; подтверждённый нодой `applied_rev` — отдельная
  колонка; кнопкой ничего применять не надо;
* на ноде применение честное: новый конфиг пишется рядом и проверяется самим
  `xray -test` — прошёл, стал рабочим и процесс перезапущен; не прошёл, рабочий
  конфиг и сервис остались прежними, а панель получила человеческую ошибку.
  Без инбаундов Xray не поднимается вовсе. Перезапуск ноды поднимает рабочий конфиг
  сам; `GET /node/status` теперь отдаёт настоящие ревизии и следит, жив ли процесс.

Проверка всего этого слоем выше — `tools/xray_test.py`: рядом с живой нодой ставится
заглушка Xray (та же форма вызова: `-test`, `-config`), панель заводит хосты и
пользователей — и сама же всё применяет, а тест сверяет файл конфига на ноде, выпущенный
tls-сертификат, перезапуски процесса и обе шкалы ревизий.

А `tools/live_demo.py` — это «попробовать руками» со всем настоящим: скачанные Xray и
Mihomo (в `bin/xray` и `bin/mihomo`, оба в `.gitignore`; `MEDUSA_XRAY_BIN` /
`MEDUSA_CLASH_BIN` задают свои пути), настоящая нода, настоящая панель. Демо заводит
две настоящие ноды (`demo` и `demo2`, каждая своим файлом состояния и своим Xray), девять
хостов на первой — vless plain / reality / wss / ws / grpc, vmess ws+tls, trojan tls,
trojan reality и ss — плюс две цепочки через обе ноды (vless reality -> trojan tls и
vless ws -> ss -> vless reality), и два подписчика. Ждёт автоприменения, а потом:

* поднимает локальный SOCKS с конфигом, собранным из ссылок самой подписки, и ходит
  внешним запросом через каждый туннель — если `generate_204` вернулось, VPN работает
  (вот здесь и проверяются vmess, trojan, ss и второй подписчик на каждом инбаунде);
* проверяет цепочки: инбаунд каждого хопа слушает на своей ноде, ключи перехода и инбаунда
  следующего хопа совпадают (выведены из одной цепочки), сертификат tls-хопа привезён
  ноде-приёмнику и его отпечаток закрепён на отправляющей ноде, правила `inboundTag`
  лежат в конфиге; туннель цепочки проверяется входом цепочки как обычным хостом подписки
  (реальность перехода подтверждает сам факт связи: без принятого хопа соседней нодой
  outbound не соединился бы); вход цепочки Clash выбирает в группе выбора наравне с
  прямым хостом; у хопа названы его же настройки — маска и принимаемые имена у reality-входа,
  свой sni (отличный от адреса хопа) и отказ от чужого SNI у tls-хопа, путь и Host-заголовок у
  websocket-входа: и в инбаунде этого хопа, и в переходе соседней ноды, и в ссылке подписчика
  (`path=`, `host=`), и туннель по этим настройкам работает настоящим Xray-клиентом;
* забирает YAML подписки (`?target=clash`), проверяет его самим `mihomo -t`, поднимает
  Mihomo, переключает группу выбора по её REST API и ходит наружу через каждый прокси.
  Reality-хосты в этой фазе туннелем не проверяются и печатаются как `NOTE`: Mihomo не
  делает рукопожатие Xray 26 (см. раздел «Что пока не сделано»), их туннель проверяет
  Xray-клиентом выше.

В конце печатаются живые ссылки со страницы подписки и адрес панели: с `--keep` панель
остаётся висеть, можно открыть её в браузере и подключаться к ней со своего клиента.
Именно этот прогон и поймал все сюрпризы Xray 26 выше — и разошёлся с Mihomo по reality.

В окне ноды конфиг можно только посмотреть: свёрнутая секция «Конфиг Xray» показывает
  тот же JSON, который панель собрала и отправила (`GET /api/nodes/<id>/config`,
приватные ключи в показе скрыты). Править его нельзя намеренно: конфиг целиком
рождается из хостов и пользователей, а случайная ручная правка разошлась бы с тем,
что реально работает на ноде.

## Что пока не сделано

* **логика самого VPN — не до конца**: рендер конфига, инбаунды и переходы цепочек уже
  есть и проверены живым Xray на двух узлах (vless, vmess, trojan и shadowsocks, два
  подписчика на инбаунд) — но hysteria2 в конфиг не попадает, а маршруты внутри ноды
  ограничены `freedom` наружу и переходом цепочки: отдельных правил по доменам, блокам или
  балансиру у панели нет;
* трафик и подписчики нод настоящие (см. раздел «Трафик и статистика»), но считают их на ноде:
  если Xray там нет или он умер сам, часть байтов теряется, и панель вместо красивых цифр честно
  показывает `trafficError`; `online`, версия агента и версия Xray нода сообщает сама — и по
  кнопке, и по фоновому опросу;
* машинная подписка есть для двух семейств (см. раздел «Форматы ссылок и Clash YAML»):
  переводные ссылки `vless/vmess/trojan/ss` (base64) и Clash YAML. Sing-box JSON
  (Hiddify, sing-box-клиенты) пока нет — ссылки sing-box понимает сам, отдельного
  конфига от панели он не просит;
* **Clash и reality поверх свежего Xray не работают** (не по вине панели): с Xray-core
  26.9.8 сервер reality отвергает ClientHello без гибрида `X25519MLKEM768`, а Mihomo
  (1.19.34 и master) этого ключа не добавляет — оба его фикса закрыты неслитыми
  (#3326, #2983). Reality-хост в YAML при этом описан правильно и работает с клиентами
  на ядре Xray (v2rayNG, v2rayN, Happ, Xray CLI) и с Xray ≤ 26.9.7; для Clash-подписчиков
  панель подсказывает заводить хосты `tls` или `ws` (подсказка в окне хоста);
* окна входа во фронтенде нет — токен читается из `localStorage['token']`;
* TLS у API ноды нет: ключ — это аутентификация, но не шифрование, так что панель и
  нода должны сидеть в одном закрытом сегменте (WireGuard/Tailscale) или за TLS-
  реверс-прокси.

## Метрики сервера на «Обзоре»

Блок «Сервер» показывает ЦП (%), ОЗУ (занято/всего) и диски (занято/всего) с полосками
загрузки; всё это автоматически обновляется каждые `pollInterval` секунд из настроек панели.
Метрики всегда запрашиваются у бэкенда, даже в тестовом режиме.

## Статистика по нодам на «Обзоре»

Вместо таблицы — «поток трафика»: сверху общая полоса, разрезанная на доли каждой ноды
(с легендой и подписями при наведении), ниже — строки нод: цветной маркер ноды (цвета
подбираются из палитры `NODE_HUES`), имя и адрес, полоса трафика относительно самой
загруженной ноды, объём и доля от общего, счётчик пользователей и бейдж состояния
«Онлайн» / «Недоступна» (недоступная нода приглушена, полоса штриховая).

## Статистика по клиентам на «Обзоре»

Тот же принцип, но в радиальном виде: SVG-кольцо разрезано на доли каждого приложения
(`Clash Verge`, `Clash Meta`, `Happ`, `v2rayNG`, `Hiddify`, `Shadowrocket`, `Streisand` —
палитра `CLIENTS`), в центре — всего подписок, рядом легенда и список строк: маркер,
название, число подписок, объём и доля трафика, счётчик активных и бейдж доли подписок.
При наведении на сегмент показывается «Clash Verge — 2 подписки». Если у пользователя
приложения нет — он попадает в корзину «прочие». В таблице пользователей к токену
добавлено название приложения.

## Трафик и статистика: как панель считает людей и ноды

Цифры берутся из Xray. Чтобы Xray считал трафик по подписчикам, в конфиге (рендер это
делает сам, `src/core/xray_config.py`) есть: `stats: {}`, `policy.levels[].statsUserUplink/
statsUserDownlink`, `api: {tag: "api", services: ["StatsService"]}` и отдельный служебный
инбаунд `dokodemo-door` (tag `api`), которому правилом маршрута запрещён выход наружу
(`blackhole` + `domain:"pattern:statsapi"` — ответ сервиса счётчиков не уходит через туннель).
Каждый клиент в конфиге имеет **метку** в поле `email`: `u<id пользователя панели>` у
подписчика и `hop<id цепочки>-<номер хопа>` у перехода. Метка — единственное, что связывает
байты ноды с человеком, поэтому `email` обязан быть непустым (правило держит рендер).

* **порт сервиса счётчиков выбирает нода, не панель**. Панель пишет туда `0`, нода ищет
  свободный петлюбочный порт (39113+) и вписывает его в рабочий конфиг (`apply_stats_port`);
  номер живёт в файле состояния и сообщается панели как `statsPort`. Наружу сервис не слушает
  никогда: `listen` обязан быть `127.0.0.1` (это отдельная проверка тестов);
* **нода читает счётчики сама и копит их у себя** (`src/node/traffic.py`): вызов
  `xray api statsquery -pattern=user>>> -reset --server=127.0.0.1:<порт>` — тем же CLI, которым
  нода проверяет конфиг. Счётчики Xray живут в памяти его процесса: перезапуск ноды, новое
  применение конфига или смерть Xray обнуляют их. Поэтому reading идёт с `-reset`, а накопленное
  нода хранит в файле состояния (`trafficBytes`, `userTraffic`, `statsAt`, `statsPort`) и
  поднимает вместе с собой;
* **снимать счётчики нода обязана перед всякой остановкой Xray** (`XrayRunner.harvest()` —
  перед `_stop()` в `apply` и при остановке ноды) и **сама, каждые `SELF_POLL_SECONDS` (15 с)**,
  не дожидаясь панели. Промежуток «не читать чаще N секунд» был и удалён: такое чтение
  пропускало байты, наработанные после прежнего чтения, и теряло их вместе с процессом Xray
  (это и поймал `xray_test`). Частоту задаёт панель — интервалом опроса, а не нода; два
  параллельных чтения (панель и самоопрос) идут под замком, иначе один и тот же кусок трафика
  попал бы в сумму дважды;
* **панель раскладывает метки по людям** (`src/panel/node_traffic.py`, таблица `node_traffic`
  `(node_id, email, user_id, bytes, updated_at)`): отчёт ноды — это метки и байты; `u<id>`
  сопоставляется с пользователем, всё остальное (транзит цепочек, метки людей, которых в панели
  уже нет) остаётся **трафиком ноды** и никому не приписывается. `used` пользователя — сумма по
  всем его нодам, `traffic` ноды — сумма её меток, `users` ноды — сколько активных подписчиков
  ей хватает её хостов и цепочек (тоже вычисляется запросом; колонки `users_count` больше нет);
* **отчёт приходит сам**: фоновый опрос (`poller._refresh`) и кнопка «Проверить связь» вызывают
  `/node/status` и пропускают ответ через `apply_status` (`read_traffic` в `node_check.py`). Если
  нода не ответила или счётчики не считались, прежние байты сохраняются, а в строке ноды
  появляется `trafficError` с человеческой причиной (нет Xray, Xray не поднят, сервис не ответил).
  Каскады честные: удаление пользователя уносит его строки трафика, удаление ноды — её часть;
  повторный отчёт ничего не удваивает (значения накопленные);
* **прежние заглушки убраны вместе с колонками**: `users.used_bytes` и `nodes.users_count`
  миграция удаляет из старых баз (`ensure_columns`), их место заняли вычисляемые значения.

Когда процесс Xray умирает, нода пересказывает его причину из его же лога (`XrayRunner._log_reason`:
последняя строка с `Failed to start` или `error` — например `bind: address already in use`), а
панель кладёт её в строку ноды (`nodes.apply_error`, на карточке — красная строка под адресом).
«Xray завершился с кодом 255, детали в логе на ноде» — это не ответ: человеку нужно видеть,
*что* именно не сработало.

Честная граница: если Xray на ноде умер сам (не по команде ноды), байты между последним снимком
и смертью процесса теряются — самоопрос ограничивает это окно пятнадцатью секундами. Своего
хранилища трафика у панели нет: она хранит только то, что подтвердила нода.

## Страница подписки

`subUrl` в настройках — адрес целиком, до `/sub` включительно (`http://127.0.0.1:8000/sub`,
`https://panel.example.com/sub`): панель дописывает к нему только токен пользователя,
никаких двойных `/sub/sub`. `GET /sub/<токен>` не требует входа — сам токен и есть пропуск.
Это один адрес с несколькими применениями: браузеру (`Accept: text/html` или Mozilla в
User-Agent) отдаётся страница, Clash и производным (UA с «clash» или `?target=clash`) —
YAML со `proxies:`, всем остальным — ссылки подписки (base64; `?raw=1` —
без base64). Именно этот адрес панель показывает в поле «Ссылка подписки», в QR и
в машинном пути `/sub/<токен>/links` (он не торгуется по Accept, но Clash по UA
всё равно получает YAML).
Бэкенд (`src/panel/routers/subs.py`) отдаёт отдельную HTML-страницу в том же стиле панели:
никнейм в заголовке, рядом — статус-таблетка (у активного пользователя с пульсирующей точкой,
как у нод «в сети»), дальше потраченный трафик и дата создания, доступные хосты (у любого
хоста, чью ссылку панель умеет собрать, — кнопка «Скопировать»: она даёт ссылку протокола
хоста для приложения — uuid пользователя или пароль, адрес хоста (не ноды!), транспорт и
защиту, а для reality ещё `pbk` из ключа хоста, `fp` (отпечаток из поля хоста, по умолчанию
chrome), `sni` (сайт-маска) и `sid` — та же логика, что и в конфиге, который панель
отправляет ноде)
и цепочки с маршрутом
(кнопка копирования даёт ссылку входа на первую ноду цепочки — остальные хопа панель
держит на своей стороне).
Язык — кнопка как в панели (глобус и текущий код RU/EN): по умолчанию русский,
клик переключает на английский (`?lang=en`). Тема — кнопка солнце/луна:
настройка панели задаёт только стартовое значение; локальный выбор живёт в
localStorage браузера (`medusa-sub-theme`) и ничего не пишет на сервер.
Отключённому пользователю
страница сообщает, что подписка не раздаётся, и хосты не показывает. На экране «Пользователи»
ссылку можно скопировать и открыть в отдельной вкладке сам.

### Машинная подписка: одна ссылка — все хосты

* `GET /sub/<токен>` — один адрес на несколько применений: браузеру (`Accept: text/html`
  или Mozilla в User-Agent) — HTML-страница; Clash и производным (UA содержит
  «clash» — Clash Verge, Mihomo proxy-provider — или явный `?target=clash`) —
  YAML со списком `proxies:` и группой выбора (Mihomo-формат: vless, vmess с `alterId: 0`,
  trojan, `ss` с шифром и паролем этого хоста, reality-opts, ws-opts, grpc-opts; tls-хосты
  с `skip-cert-verify: true`, ибо сертификаты нод самоподписанные);
  всем прочим — все ссылки хостов разом: base64-строка из переводных строк
  (`vless://`, `vmess://` (base64 JSON), `trojan://`, `ss://`; формат ждут v2rayN, v2rayNG,
  Happ, Hiddify, Shadowrocket и большинство клиентов), `?raw=1` — те же строки без base64.
* `GET /sub/<токен>/links` — то же, но без переговоров по Accept: всегда список
  ссылок (Clash-UA всё равно получает YAML).
  `Cache-Control: no-store`. Отключённому пользователю и чужому токену — 404.
* `GET /sub/<токен>/qr/subscribe` — QR (SVG, генерирует `segno`, чисто питоновский
  модуль без картинок) на машинную ссылку: вставил адрес в приложение или
  отсканировал — все хосты добавились. QR ведёт на тот же адрес, что открыт в
  браузере (`subUrl` + токен; `subUrl` пустая — адрес, с которого открыта
  страница) — иначе телефон не попадёт домой.
* `GET /sub/<токен>/qr/host/<id>` — QR на ссылку одного хоста; `<id>` принимает
  и вход цепочки (тот же `hosts.id`, имя в ссылке — имя цепочки).
* На самой странице: секция «Ссылка подписки» (поле с адресом + копирование +
  кнопка QR) и у каждого хоста/цепочки — кнопка «QR-код», открывающая модалку
  (`#qrdlg`, `<dialog>`) с этим QR; сама картинка QR на странице не рисуется —
  только по кнопке. Модалка и скрипты темы/QR живут в самой
  странице (`THEME_JS`/`QR_JS` в subs.py) — фронтенд панели им не нужен.

### Форматы ссылок и Clash YAML

Всё, что понимает подписчик, собирается в одном месте — `src/panel/subscription.py`
(чистые функции: токен + строка хоста → ссылка или YAML; ни БД, ни сети). Ссылка обязана
описывать ровно то, что рендер положил в конфиг Xray: тот же `uuid5`, тот же пароль, тот
же короткий id reality, адрес хоста (не ноды!), транспорт и защита. Ссылка расходится с
конфигом — подписчик не подключится, поэтому расхождение здесь ошибка, а не мелочь.

| протокол | ссылка | прокси в Clash YAML |
| --- | --- | --- |
| vless | `vless://<uuid>@адрес:порт?type=tcp&encryption=none&security=…` | `type: vless`, `uuid` |
| vmess | `vmess://` + base64 JSON (`v2`, `id`, `aid:"0"`, `scy`/`cipher: auto`, `net`, `path`, `host`, `tls`) | `type: vmess`, `cipher: auto`, `alterId: 0` |
| trojan | `trojan://<пароль>@адрес:порт?security=tls&sni=…` (или reality-параметры) | `type: trojan`, `password` |
| shadowsocks | `ss://<метод>:<пароль этого хоста>@адрес:порт` | `type: ss`, `cipher`, `password` |

* reality в ссылке: `pbk` (публичный ключ хоста), `sni` (сайт-маска), `fp` (отпечаток,
  по умолчанию chrome), `sid` (короткий id подписчика, `reality_short_id`) и `spx`;
* отпечаток (`fp`) и поля транспорта (`path=`, `host=`, `serviceName=`) едут и в конфиг,
  и в ссылку — только если заданы; при защите «none» отпечатка нет и отправить нельзя;
* Clash YAML содержит ещё группу выбора (`proxy-groups`, `type: select`, все хосты) и
  правило `MATCH,<группа>`: одиночный Mihomo/Clash Verge без группы не знает, куда класть
  трафик. `external-controller` и порты панель не назначает;
* reality в YAML называет сайт-маску обоими полями (`servername` и `sni`): Mihomo для
  reality берёт `sni`, а не `servername` — живой прогон показал, что с одним лишь
  `servername` он стучался с sni = адрес ноды и получал чужой сертификат;
* hy2 (hysteria2) ссылки не имеет и хостом не заводится — честный `400`, а не хост,
  о котором подписчик не узнает.

## Цепочки: переход трафика между нодами

Цепочка — несколько нод подряд. Она живёт в таблице `hosts` своими строками, по одной на
каждый хоп: `hop_index` 0 — вход, 1.. — промежуточные хопа, `-1` — обычный хост. Человек в
`GET /api/hosts` видит только вход (имя — имя цепочки, `chain` — id цепочки): к нему он
подключается, ему отдаётся ссылка подписки и QR. Промежуточные хопа — та же таблица hosts,
но наружу они не показываются (`hosts.VISIBLE`), их нельзя править и удалять поодиночке
(`409`): цепочка правится целиком через `PATCH /api/chains/{id}`, и правка пересобирает все
её хопа (имена, ноды, порты, адреса и ключи).

Что из этого выходит в конфиге (`render_node_config(node, hosts, users, chains)`):

* **инбаунд каждого хопа на своей ноде.** Тег инбаунда — имя хопа: вход носит имя цепочки,
  дальше `«цепочка hop N»`; по нему видно в логе Xray, какой переход какой цепочки обслужил
  трафик. Порты хопа занимают ноду наравне с хостами (`UNIQUE (node_id, port)`), хотя
  человеку не показываются;
* **ключи перехода выводятся из цепочки, а не из подписчика**: `hop_uuid`, `hop_password`,
  `hop_short_id` — uuid5/пароль/короткий id от `medusa-chain-<chain id>-hop-<номер>`. Одной
  и той же функцией панель собирает инбаунд ноды-приёмника и outbound ноды, которая в этот
  хоп стучится, — разойтись они могут только вместе. Подписчик различается на **входе**
  цепочки (свой uuid, пароль, короткий id), на промежуточных хопа трафик общий: отдельного
  outbound на каждого человека не заводим;
* **outbound в следующий хоп**: адрес — **адрес самого хопа** (`Hop.address` в запросе,
  `hosts.address` в базе), а если человек его не назвал — адрес ноды этого хопа. Соседняя нода
  обязана прийти туда же, куда панель отправляет человеку ссылку на вход цепочки: иначе
  «человек подключается по одному адресу, а внутри цепочки трафик идёт по другому». tls-хопу
  сертификат выпускается на это же имя, поэтому SNI соседа и имя в сертификате не расходятся.
  Протокол/порт/транспорт/защита — из строки этого хопа. Формат settings диктует Xray:
  `vnext` у vless и vmess, `servers` у trojan и shadowsocks (Xray 26 прямо отказывает
  trojan с `vnext`: «\"servers\" should have one and only one member»);
* **маршрут по `inboundTag`**: `routing.rules = [{inboundTag: [инбаунд хопа], outboundTag:
  переход}]`. Без этого трафик, вошедший в цепочку, ушёл бы наружу напрямую. У последнего
  хопа правила нет — он выходит через `direct`;
* **tls-хопу сертификат выпускает панель** (`src/panel/host_keys.py`), привозит его ноде
  вместе с конфигом (подсказка `certs` с `certificate`/`privateKey` — нода кладёт как есть,
  закрытый ключ 0600) и закрепляет отпечаток в outbound соседней ноды:
  `tlsSettings.pinnedPeerCertSha256` (строка, не массив). Иначе никак: Xray 26 выбросил
  `allowInsecure` («migrated to pinnedPeerCertSha256») и самоподписанный сертификат «на
  веру» не принимает. Выпуская сертификат самой, панель знает его отпечаток в момент сборки
  обоих конфигов — не нужно сначала применить конфиг на одной ноде и выведать у неё факт;
* **reality-хоп**: у входа цепочки короткие id подписчиков (как у обычного reality-хоста) и
  своя пара x25519, у промежуточного хопа — один короткий id на весь переход
  (`hop_short_id`), публичный ключ инбаунда уходит в outbound соседней ноды;
* **нода может встретиться в цепочке не подряд** (`A -> B -> A` законно, соседние хопы на
  одной ноде — `400`): у неё тогда несколько отдельных инбаундов и переходов.

**Что настраивается у хопа:** нода, протокол, транспорт (`tcp/ws/grpc`), защита
(`none/tls/reality`), порт, **свой адрес** и **все детали защиты и транспорта этого хопа** —
`dest` и `serverNames` (reality), `sni` и `rejectUnknownSni` (tls), `path`/`hostHeader` (ws),
`serviceName`/`grpcAuthority` (grpc), `fp` (utls-отпечаток клиента). Хоп — строка той же
таблицы `hosts`, поэтому колонки у него те же, что у обычного хоста, и правила те же:
поле чужой защиты или чужого транспорта — `400` (`src/panel/field_rules.py` — общий с
окном хостов), отпечаток при защите `none` — `400`, свой сертификат хопу нельзя —
`400` (панель обязана знать его отпечаток, чтобы закрепить за соседней нодой).

Правило, которое держит рендер: **у перехода нет своих деталей — есть детали хопа-приёмника.**
`hop_outbound()` берёт транспорт, защиту, sni, путь, Host, имя сервиса, маску, отпечаток и
отпечаток сертификата из строки того хопа, куда идут; `transport_settings()` одна и та же для
хоста и для хопа. Инбаунд этого же хопа собирается из его же строки — обе стороны перехода
разойтись не могут. Исключение — reality: маска (`dest`) нужна серверу, поэтому она в
инбаунде этого хопа, а клиенту перехода нужен `serverName`, под которым притворяются: панель
берёт хост из `dest` этого же хопа (у обычного reality-хоста — из его `dest`; если `dest`
пустой и назван `sni` — он тоже подходит, ибо маскируется им).

Имя для tls-хопа (`chain_hops.hop_server_name`): `sni`, если человек его назвал,
иначе адрес хопа, иначе адрес ноды. Под это же имя панель выпускает сертификат, его же
ставит в `tlsSettings.serverName` переходу и его же требует сосед (`rejectUnknownSni`).
Смена sni хопа перевыпускает сертификат (`reissue_hop_certs`), иначе сосед называл бы имя,
которого в сертификате нет.

Окно цепочки показывает детали хопа внутри его же ряда: блок защиты и «настройки транспорта»
(`renderHopCfg`/`hopCfgBody` в `script.js`, `.hopsec`/`.hopadv` в `style.css`, свёрнуты,
как в окне хоста), при смене защиты/транспорта они перерисовываются на месте, при смене
ноды порт хопа подобряется свободным (`setHopPort`), пустая строка при правке — сброс к
умолчанию.

**Адрес хоста у хопа обязателен и подставляется сам** (`chain.hopAddress` в `script.js`, `setHopAddress`/`hopAddress`):
это тот адрес, куда подключатся и подписчик входа, и соседняя нода, поэтому панель пишет в поле адрес
ноды этого хопа — пустого ряда не бывает, и человек видит настоящий адрес, а не угадывает. Названный
адрес совпал с адресом ноды — в базу уходит `null`: «пусто = адрес ноды» означает «следуй за нодой»,
и переезд ноды не оставляет цепочку со старым адресом. Свой, названный человеком адрес (`fi.example.net`)
сохраняется как есть.

Удаление цепочки снимает её инбаунды и переходы на всех затронутых нодах (каскад по
`hosts.chain_id` + пересылка конфигов), правка цепочки помечает грязными и старые, и новые
её ноды.

**Прежние базы дорисовываются сами** (`db.ensure_chain_hops`): у старой цепочки был только
хост входа, поэтому миграция помечает его хопом 0, заводит недостающие хопа и выдаёт им
ключи (reality — пару x25519, tls — сертификат с отпечатком), после чего помечает грязными
те ноды, которым есть что отправить. Без этого старая цепочка молча осталась бы одним хостом,
а её reality-вход уехал бы на ноду с пустым приватным ключом. Проверка — в `panel_test`
(«прежняя база поверх новой панели»).

Занятость порта хопом держит индекс `hosts_node_port` (`UNIQUE (node_id, port)`), заведённый
`ensure_columns` — он достался и новым, и прежним базам (в прежних Хопа отдельных строк hosts
не было, и дубликат портов там возможен: индекс поверх дубликата sqlite не создаст, но
проверка слоем выше держит порт занятым всё равно).

**Окно «Конфиг Xray» (`GET /api/nodes/<id>/config`) прячет секреты целиком**
(`config_push.mask_secrets`): не только приватные ключи reality у инбаундов, но и пароли
 trojan/shadowsocks/vmess и ключи подписчиков — и у инбаундов, и у переходов цепочек
(у перехода свой пароль и свой x25519). Проверяется по-честному: сравнение паролей хопов
`panel_test` делает по `collect()` — по тому же словарю, что реально уезжает ноде, а не по
замаскированному показу.

## Порты: занятость считается по машине ноды, а не по одной ноде

Две ноды с одним адресом — это одна машина (несколько контейнеров на одном хосте, несколько
адресов наружу). Xray половинки конфига не поднимает: при `bind: address already in use` он
падает целиком, и у ноды останавливаются **все** хосты, включая те, что вчера работали. Поэтому
`src/panel/ports.py` смотрит на пару (адрес ноды, порт) и считает занятым:

* порт любого хоста любой ноды на том же адресе (включая скрытые хопа цепочек);
* **API-порт любой ноды на том же адресе** — он слушает там же и забирает порт до Xray.

Проверка живёт в слое выше: `POST/PATCH /api/hosts`, `POST/PATCH /api/chains`, `POST/PATCH
/api/nodes` (переезд ноды на другой адрес проверяется по её хостам тоже) — `409` с человеческим
текстом: «порт 8443 на 10.9.2.1 уже занят API-портом ноды «machine-a» — Xray на этой машине не
поднимется». Фронт держит то же правило для подсказки (`taken()` в `script.js` учитывает
API-порты нод той же машины), но решает бэкенд.

Миграция прежних баз (`free_hop_ports` в `db.py`) убирает хопа с занятого порта на первый
свободный, записывает новый порт и в ряд хопа, и в `chains.hops` (иначе окно правки показывало бы
порт, которого больше нет), и печатает в лог панели, что и почему сдвинуто. Порты обычных хостов
миграция не трогает: их выбирал человек.

## Хосты цепочек подсасываются из цепочек

Хост цепочки — её вход (хоп 0) и её название: он лежит в `hosts` рядом с остальными хостами
и отдаётся в `GET /api/hosts` с полем `chain`. Поэтому переименование, правка хопов или
удаление цепочки сразу видны в «Хостах» — расхождений «человек видит одно, нода работает по
другому» не остается. В тестовом режиме то же самое делает `hostsView()` в
`src/panel/static/script.js`.

## Ноды

Карточка ноды нарочно бедная: название, адрес с портом API, «Онлайн/Недоступна», версия
ноды и версия `Xray` — и надпись «изменить ноду», потому что вся карточка это кнопка.
Версии сюда пишутся с самой ноды: пока панель её не проверила, вместо версий стоит
«ещё не сообщались». Ни API-ключа, ни ссылки на API ноды на карточке нет.

Клик по карточке открывает окно правки ноды: сверху — имя ноды и её статус (тот же самый
бейдж, что на карточке), ниже — поля названия, адреса, порта API и API-ключа (ключ вписан
целиком, как адрес и порт; под полем — его отпечаток), ещё ниже — версия ноды, версия
`Xray` и время последней проверки связи. Заголовок окна остаётся прежним, пока правку не
сохранили: «изменилось» должно быть видно только тогда, когда оно действительно сохранено.

Имя ноды менять можно: хосты и цепочки держатся за `node_id`, а имена хопов читаются из
базы заново, поэтому переименование их не ломает (в списке уже занятое имя — `409`).

## Как панель договаривается с нодой

Нода — отдельная программа на своём порту (по умолчанию 9443), панель ходит к ней сама.

1. Нода при первом запуске создаёт API-ключ (`sk-api-…`, 256 бит), пишет его в свой файл
   состояния `MEDUSA_NODE_STATE` (права 0600) и один раз печатает его в лог — целиком и
   крупно, чтобы не пропустить. Тот же ключ покажет `medusa-node --print-api-key`.
2. Администратор переносит этот API-ключ в панель («Добавить ноду» или `POST /api/nodes`):
   без него ноду не создать — панель без ключа не сможет сделать на ноде ничего.
3. Панель ходит на `http://адрес:apiPort`:
   * `GET /node/health` — без ключа. Нужен, чтобы различать «нода не отвечает» и
     «ключ не подходит». Отдаёт роль (`medusa-node`), версию агента и отпечаток ключа —
     имени ноды в ответе нет;
   * `GET /node/identity`, `GET /node/status`, `PUT /node/config` — только с
     `Authorization: Bearer <ключ>`; `/node/status` приносит и трафик: `trafficBytes`,
     `userTraffic` (`[{email, bytes}]`), `statsAt`, `statsPort`, `statsError`.
4. Отпечаток (`sha256` ключа, первые 10 hex, в виде `a1b2c-3d4e5`) — это то, по чему
   панель и нода понимают, что речь об одной и той же ноде. Имени ноды нода не знает
   совсем: «домашняя», «vps-fi» — выдумка панели, она нужна только чтобы называть ноду в
   хостах и цепочках. Сам API-ключ наружу не отдаёт никто: ни нода, ни панель (в списках
   только masked-форма; настоящий ключ — отдельным запросом `GET /api/nodes/{id}/key`).
5. Если панель меняет адрес, порт, API-ключ или прокси ноды, прежнее «в сети» сбрасывается:
   связь считается подтверждённой только после новой проверки.

### SOCKS5 для связи с нодой (`nodes.api_proxy`)

Нода может сидеть за NAT или быть доступна только через прыжок. Тогда у ноды вписывается
socks5-прокси — это настройка **каждой ноды** (поле «SOCKS5-прокси для связи» в окне ноды и
в окне добавления), а не настройка панели:

* форма — `socks5://[user[:pass]@]host:port` (`src/panel/proxy_url.py`); принимается и
  `socks5h` — с резолвом имени на стороне прокси. Человек может написать просто `host:port`;
  порт по умолчанию 1080; в базе значение нормализованное, пустая строка — «ходи напрямую».
  Чужие схемы (http/https) панель отвергает `422` человеческим текстом: API ноды и так http,
  а socks5 переключает голый TCP и подходит к любому адресу ноды;
* прокси касается только связи панели с API ноды: кнопка «Проверить связь», фоновый опрос
  (`poller`) и доставка конфига (`config_push`) собирают один и тот же `NodeTarget` и идут
  одним же путём — статус ноды не должен зависеть от того, кто именно его запросил, и от
  того, есть ли прокси;
* пароль нигде не показывается: в списках нод и в текстах ошибок — masked-форма
  (`socks5://med:••••@j.example:1080`), целиком прокси отдаёт только
  `GET /api/nodes/{id}/proxy` (под `writer`, как и ключ ноды) — иначе сохранение диалога
  выглядело бы как «прокси без учётки»;
* отказ прокси панель называет отказом прокси: «нода … не ответила: панель идёт через прокси
  …, и он не отвечает» или «прокси … не пустил к ноде …». Иначе человек пошёл бы чинить
  Xray на ноде, которая ни при чём;
* на самой ноде прокси не нужен и неизвестен ей: нода к панели не приходит.

`tools/socks5.py` — маленький настоящий socks5-сервер для проверок (только CONNECT, ведёт
журнал `connections`, умеет username/password по RFC1929 и режим «следующий запрос оборвать»);
`.venv/bin/python tools/socks5.py user pass` поднимает его отдельным процессом и печатает свой
адрес — этим пользуется `tools/ui_test.mjs`.

Контракт обмена лежит в `src/core/contract.py`, API-ключи и отпечатки — в `src/core/api_keys.py`.
Его используют обе стороны, поэтому разъехаться они могут только вместе.

Состояние ноды переживает перезапуск: API-ключ и последние ревизии лежат в файле состояния.
`MEDUSA_NODE_API_KEY` перебивает записанный ключ — так можно зафиксировать ключ секретом в
оркестраторе, не теряя связи с панелью.

## Опрос нод

Кнопка «Проверить связь» — ручная проверка. Но статус должен быть свежим и без кликов,
поэтому панель ходит к нодам сама (`src/panel/poller.py`): каждый круг она перечитывает
настройки и обходит все ноды, у которых есть API-ключ. Ноду без ключа панель не спрашивает
— без ключа она увидела бы только «что-то отвечает», а это не статус ноды.

* интервал — настройка «Опрос нод» (`settings.pollInterval`, секунд), таймаут ответа —
  «Таймаут ответа» (`settings.nodeTimeout`): оба читаются на каждый круг, поэтому смена
  настройки действует сразу, без перезапуска панели;
* поход к ноде один и тот же для кнопки и для опроса (`src/panel/node_check.py`): витрина
  `/node/health` без ключа, затем `/node/identity` с ключом. Статус не должен зависеть от
  того, кто именно его запросил;
* «в сети» становится только при полной связке (нода отвечает и API-ключ её). Если нода
  отвечает чужому ключу, для панели она бесполезна — значит, не в сети;
* версия Xray не исчезает из-за одного неудачного похода, а `seen_at` двигается только
  когда нода правда отвечала;
* опрос можно выключить совсем: `MEDUSA_NODE_AUTO=0`.

Открытая страница перечитывается с тем же интервалом: панель опрашивает ноды в базе, а
человек смотрит на страницу. Страница «Настройки» не перерисовывается (там черновик
формы), не перерисовывается ничего, пока открыто окно правки или пока пользователь печатает,
и ничего не обновляется, если вкладка скрыта.

## Учётки, роли и сессии

Панель без учётки не работает: вход `POST /api/login` выдаёт токен сессии, фронт держит его
в `localStorage` и подставляет в `Authorization`. Без сессии API отвечает `401`, а панель
показывает окно входа — закрыть его нельзя, можно только войти (или выйти ключом).
Срок сессии — настройка `Сессия, часов`; «Выйти» в сайдбаре удаляет именно вашу сессию.

Владелец создаётся вместе с базой (`MEDUSA_ADMIN_USER` / `MEDUSA_ADMIN_PASSWORD`; без
пароля генерируется и печатается в лог один раз). Он один, и он защищён:

| Роль | Панель | Другие учётки | Себя |
| --- | --- | --- | --- |
| **владелец** | всё | создаёт, отключает, удаляет | пароль; состояние и удаление — нельзя |
| **администратор** | ноды, хосты, цепочки, пользователи, настройки | только смотреть | пароль и свои ключи |

Роли в панели две: новая учётка всегда администратор, роль никто ни себе, ни другим не меняет.

Держит бэкенд, а не только интерфейс (`src/panel/deps.py`, `src/panel/routers/admins.py`):

* `writer` (владелец и администратор) — на всякую запись, `owner_only` — на чужие учётки;
* состояние чужой учётки меняет только владелец; администратору доступно только своё,
  отключить самого себя нельзя (`403`);
* **пароль меняет только владелец аккаунта** — никто, включая владельца панели, чужой пароль
  не меняет (`409`); при смене пароля чужие сессии этого аккаунта выбиваются, своя остаётся;
* владельца нельзя отключить, удалить или переписать его пароль (`409`);
* отключённый аккаунт не входит ни паролем, ни ключом, а его живые сессии удаляются сразу;
* `GET /api/nodes/{id}/key` (API-ключ ноды целиком) — только тем, кто может писать:
  ключ даёт управление нодой.

Интерфейс повторяет эти границы, чтобы не спотыкаться о кнопки: в списке администраторов
доступна только своя строка (чужие — только владельцу), в диалоге аккаунта выключено то,
что этому человеку не разрешено. `MEDUSA_AUTH=0` выключает учётку целиком — только для разработки на
своей машине (панель тогда открыта любому, кто до неё достучится).

## Вход по аппаратному ключу (FIDO2)

Настройка `Вход по аппаратному ключу` (`passkeyEnabled`) разрешает входить ключом
(YubiKey и прочее, WebAuthn) вместо пароля. Ключ записывается на учётку: владельцу и
администратору — своему, остальным — только владельцу. Запись и вход — обычное
рукопожатие WebAuthn в браузере (`navigator.credentials.create()` / `.get()`), панель отдаёт вызовы и
проверяет ответы.

Что проверяет панель (`src/panel/fido2.py`, своей верификационной библиотеки нет —
`cryptography` + `cbor2`):

* вызов живёт пять минут, одноразовый, хранится в базе (`fido_challenges`) и сгорает
  при использовании: повторить ответ нельзя;
* `origin` ответа обязан совпасть с адресом панели (с учётом `MEDUSA_PANEL_BASE`, когда
  панель за обратным прокси), `rpId` — с её доменом;
* флаг присутствия аутентикатора и подпись ответа — открытым ключом конкретного ключа;
  подпись не тем ключом, незаписанный ключ и отключённая учётка → `401`;
* алгоритмы: ES256 и EdDSA; аттестат — `none` или `packed` (x5c), производителей ключей
  панель не выбирает: credential'ы с любого устройства принимают, важны подпись и вызов;
* счётчик аутентикатора: если ключ его ведёт, он обязан расти (клон ключа попадёт на
  уменьшение счётчика); ключи без счётчика (например некоторые приложения-аутентикаторы)
  панель не блокирует;
* наружу панель отдаёт ник, алгоритм, aaguid, счётчик подписей и дату — сам открытый ключ
  и вызовы не показываются.

В базе: `admin_keys` (открытый ключ в PEM, алгоритм, aaguid, `sign_count`, ник) и
`fido_challenges`. Приватных ключей панель не хранит и не создаёт.

`navigator.credentials` работает только в защищённом контексте — HTTPS или `localhost`.
На `http://127.0.0.1` браузер ключи отдаёт, на `http://адрес-в-сети` — нет: панель честно
скажет «нужен HTTPS».

## Настройки панели

Настройки живут в базе (`GET/PATCH /api/settings`) и поэтому переживают перезагрузку и
другой браузер. В `localStorage` лежат их кэш (`medusa:settings`) и несохранённый черновик
формы (`medusa:settings:draft`) — так выбранная тема не теряется, а недописанная форма не
пропадает:

* тема применяется сразу при выборе;
* остальные поля сохраняются кнопкой «Сохранить», несохранённое помечается флагом
  «не сохранено» и точкой на пункте «Настройки»;
* язык интерфейса — `localStorage['medusa:lang']`;
* срок сессии (`sessionHours`) и разрешение входа по аппаратному ключу (`passkeyEnabled`)
  лежат в этой же строке настроек: см. раздел «Вход по аппаратному ключу (FIDO2)».

## Docker

Образы: `deploy/Dockerfile.panel` (панель) и `deploy/Dockerfile.node` (нода + Xray).
Контекст сборки — корень репозитория, `.dockerignore` выбрасывает базу, venv и тулзы.

```bash
docker build -f deploy/Dockerfile.panel -t medusa-panel .
docker build -f deploy/Dockerfile.node  -t medusa-node  .
docker compose -f deploy/docker-compose.yaml up --build      # панель + нода на одной машине
```

Образ панели копирует из `src/` только `src/panel` и `src/core`, образ ноды — только
`src/node` и `src/core`: код одной половины в контейнер другой не попадает ни при каких
обстоятельствах. Xray в образ ноды берётся из `ghcr.io/xtls/xray-core` и фиксируется
тегом через `ARG XRAY_IMAGE` (по умолчанию `26.9.9` — на нём панель проверялась живым
прогоном): `docker build -f deploy/Dockerfile.node --build-arg XRAY_IMAGE=ghcr.io/xtls/xray-core:<версия> -t medusa-node .`

## CI/CD (GitHub Actions)

```
.github/workflows/ci.yml        # push в develop и main + pull request в них
.github/workflows/release.yml   # push в main: образы в docker.sonoma.su + релиз GitHub
```

**`ci.yml` — проверки при пуше** (`develop`, `main`, pull request в них, и вручную):

* `tests` — те же наборы, что гоняет `./tools/run_all.sh` (границы монолита, нода, рендер
  конфига Xray и применение к тестовой ноде, права/сессии/FIDO2, панельный API с живой связкой,
  фронт против живого API (`ui_test.mjs`) и моковые сценарии), но **каждым шагом отдельно**:
  в интерфейсе Actions сразу видно, какой набор упал, вместо «умерла одна большая инструкция».
  Python — `actions/setup-python` с 3.14, затем
  `pip install uv && uv sync --frozen` (`.venv` в корне — его и зовёт run_all.sh); Playwright
  ставится в самом джобе (`npm ci` в `tools/` + `npx playwright install --with-deps chromium`).
  `astral-sh/setup-uv` не используется: у него нет тега `v8`/`v9`/`v10` целиком, только
  `v10.3.3`, а мажорные теги заканчиваются на `v7` — ссылка `@v10` ломает «Unable to resolve
  action» прямо на «Set up job» и оба джоба падают, не доходя до тестов;
* `docker-build` — сборка обоих образов **без публикации**: ловит поломку Dockerfile и
  держит границы COPY (в образ ноды просто нечего копировать, если поехал не туда);
* `live` — `.venv/bin/python tools/live_demo.py` со скачанным `bin/xray`. Стоит
  `continue-on-error: true`: прогон зависит от поведения свежего Xray (панель проверялась на
  26.9.x), поэтому сигналит о расхождении, но не блокирует merge. Mihomo в CI не качается —
  `live_demo` сам честно печатает SKIP по clash-фазе, туннели проверяет Xray-клиентом.

**`release.yml` — merge в main = релиз.** Версия берётся **из `pyproject.toml`** (та,
что уже в main), и из неё: тег `v<версия>`, релиз GitHub на этом коммите и два образа в
свой контейнерный реестр — `docker.sonoma.su/<namespace>/panel` и
`docker.sonoma.su/<namespace>/node`, каждый с метками `<версия>`, `<мажор>.<минор>` и
`latest`. Реестр закрытый, вход в него — обычный `docker login` (логин + пароль).

Что заводится руками (Settings → Secrets and variables → Actions):

| Где | Имя | Что это |
| --- | --- | --- |
| **SECRETS** | `REGISTRY_PASSWORD` | пароль для `docker login docker.sonoma.su` |
| VARIABLES | `REGISTRY_USERNAME` | логин в реестре (можно и секретом — workflow принимает оба) |
| VARIABLES | `REGISTRY` | адрес реестра; по умолчанию `docker.sonoma.su` |
| VARIABLES | `REGISTRY_NAMESPACE` | путь внутри реестра: `docker.sonoma.su/<namespace>/panel`; по умолчанию `medusa` |

Переменные — не секреты: это адреса и пути, их видно в логах, и менять их должен человек,
а не CI. Пароль — только SECRETS.

`secrets` и `vars` в `release.yml` читаются **внутри шагов**, а не в workflow-level `env`:
в workflow-ом `env` эти контексты не разрешены, и файл с `secrets.…` на уровне workflow GitHub
вообще не запускает — прогон заканчивается «failure» без единого джоба.

Ограничение, о котором стоит помнить: GitHub-раннер доверяет только публичным CA, поэтому
у `docker.sonoma.su` обязан быть настоящий TLS-сертификат (или реестр должен быть доступен
по 443 с валидным сертификатом) — иначе `docker login` в джобе сорвётся ещё до публикации.
Если сертификат самоподписанный, публикацию придётся гонять runner-ом у себя (self-hosted) или
класть в образ доверенный корень — молча «починить» это workflow-переменной нельзя.

Тег и релиз делаются штатным `GITHUB_TOKEN` (джобе выдано `permissions: contents: write`) —
того же секрета не требуют. Релиз на `main` запускается только по push (`workflow_dispatch`
— вручную); pull request релиза не делает. `develop` в триггерах стоит не ради релиза, а ради
честного статуса: GitHub заводит прогон и на пуш в develop (в тот самый пуш, когда файл
появился в репозитории), и без ветки в фильтре такой прогон заканчивается «failure» без единого
джоба. На develop джоб `version` не проходит свою `if` (нужен `refs/heads/main`), а `images` и
`release` нужны `version` — значит вся цепочка пропускается, и прогон зелёный.

**Без доступа к реестру релиз всё равно будет.** Джоб `images` сначала проверяет, что
логин и пароль заданы (`Логин и пароль к реестру заданы?` — там же человеческий текст вместо
`Password required`, и предупреждение, если `$REGISTRY/v2/` не отвечает раннеру), а джоб
`release` идёт по `if: !cancelled()`: тег `v<версия>` и релиз GitHub появляются даже когда
публикация образов упала, и в теле релиза в этом случае напечатано, что именно не выложилось.

**Повторный merge без новой версии релиза не плодит:** джоб `version` смотрит, есть ли уже
тег `v<версия>` на origin, и если есть — тег и релиз пропускаются, а образы пересобираются и
публикуются (пуш в main значит «эти образы актуальны»). Поэтому выпуск версии = правка
`version` в `pyproject.toml` (она одна на панель и на ноду: `src/core/version.py`, `src/panel/meta.py`
и `GET /api/meta` читают её же).

Xray, который едет в опубликованный образ ноды, задаётся одной строкой — `env.XRAY_IMAGE` в
`release.yml`, и он же уходит в `--build-arg XRAY_IMAGE`: сборка в CI и локальная сборка должны
получать один и тот же Xray, иначе «что опубликовано» и «что проверяется» разойдутся.

Чтобы merge в main был только зелёным, в branch protection на `main` (и на `develop`, если
хотите) стоит задать required checks по именам джобов `ci.yml`:
`Панель, нода, конфиг Xray и фронт`, `Сборка образов (без публикации)` (`live` — не required,
он справочный).

### Нода на другой машине

Проще всего собрать там, где запускать — репозиторий маленький, сборка недолгая:

```bash
# на машине ноды
git clone https://github.com/saddydead1/medusa && cd medusa
docker build -f deploy/Dockerfile.node -t medusa-node .

docker run -d --name medusa-node --restart unless-stopped \
  --network host \
  -v medusa-node:/var/lib/medusa-node \
  -e MEDUSA_NODE_PORT=9443 \
  -e MEDUSA_NODE_API_KEY="sk-api-..." \
  medusa-node
docker logs medusa-node        # ключ задан? нода напечатала свой — взять его в панель
```

`--network host` (он же в docker-compose.yaml) обязателен: ноде нужно слушать и API-порт,
и клиентские порты Xray, которые панель выбирает сама. Открыть брандмауэр: API-порт
и порты хостов. Если нода строится на машине другой архитектуры, чем VPS:
`docker build --platform linux/amd64 ...` (для ARM-VPS — `linux/arm64`).

Вариант «собрать один раз, раздавать много раз» — реестр:

```bash
docker login ghcr.io
docker buildx build --platform linux/amd64 -f deploy/Dockerfile.node \
  -t ghcr.io/<you>/medusa-node:latest --push .
# на ноде: docker pull ghcr.io/<you>/medusa-node:latest && docker run ...
```

(или без реестра: `docker save medusa-node | gzip > node.tar.gz`, `scp`, `docker load`).

Панель — обычный контейнер с портом и томом для базы:

```bash
docker run -d --name medusa-panel --restart unless-stopped \
  -p 8000:8000 -v medusa-panel:/data \
  -e MEDUSA_ADMIN_USER=admin \
  medusa-panel
docker logs medusa-panel   # панель напечатает пароль владельца: без MEDUSA_ADMIN_PASSWORD она его генерирует сама
```

Сборок на этой машине не проверялись: Docker-клиент есть, демона нет. А вот граница
импортов проверена `arch_test.py` — именно он не даст панели и ноде случайно узнать
друг про друга больше, чем нужно.

**Панель и нода на одной машине — панель тоже на host-сети** (так стоит в
`deploy/docker-compose.yaml`): панель ходит к ноде по её API-порту, и пока панель в
bridge-контейнере, `127.0.0.1` в карточке ноды означает «сам контейнер панели» — связка не
складывается (`нода …:9443 не ответила: ConnectError`). На host-сети адрес ноды в панели —
`127.0.0.1`. Если панель принципиально держат в bridge с `ports:`, ей нужен адрес хоста:
`extra_hosts: ["host.docker.internal:host-gateway"]` и `host.docker.internal` в карточке ноды
(или IP `docker0`, что то же самое, только без имени). Порт панели — `MEDUSA_PANEL_PORT`.


## Проверки

```bash
./tools/run_all.sh                    # тестовая нода на своём порту + тестовая панель на временной базе
MEDUSA_LIVE=1 ./tools/run_all.sh      # то же + живой прогон скачанными Xray и Mihomo (bin/)
./tools/live_demo.py                  # живой прогон отдельно: туннели, подписка, Clash
```

* `tools/arch_test.py` — границы монолита: панель не импортирует `src.node`, нода не
  импортирует `src.panel`, ядро не импортирует ни того, ни другого;
* `tools/node_test.py` — нода сама по себе: API-ключ генерируется и переживает перезапуск,
  файл состояния 0600, без API-ключа `/node/identity` закрыт, чужой API-ключ отвергнут,
  наружу не уходит ни кусочка ключа (только отпечаток), имени ноды в ответах нет; трафик:
  нода подобрала петлюбочный порт счётчиков и вписала его в рабочий конфиг, снятые счётчики
  складываются по меткам (uplink+downlink, пустое значение после `-reset` = 0), новые байты
  прибавляются к накопленным, всё это переживает перезапуск ноды (файл состояния 0600), а если
  Xray не поднят или бинарника нет — прежние байты остаются и появляется честная `statsError`;
  отдельно смерть Xray после запуска: нода пересказывает его же строку из xray.log
  («bind: address already in use»), а не прячет за «детали в логе»;
* `tools/panel_test.py` — панель без браузера: CRUD, конфликты портов и имён (в том числе
  переименование ноды), цепочки и их хосты, вход, сессии, защита владельца, поведение при
  `MEDUSA_AUTH=1`, API-ключ ноды (он обязателен, не снимается и не светится в ответах),
  фоновый опрос (интервал из настроек, нода без ключа не опрашивается, «в сети» только при
  правильном ключе) и живая связка с тестовой нодой: «ключ подходит», «ключ не тот»,
  «нода не отвечает»; отдельно учёт трафика: метки ноды раскладываются по людям, транзит
  цепочек и метка человека, которого в панели нет, остаются трафиком ноды, повторный отчёт
  ничего не удваивает, причина «счётчики не считались» доходит до строки ноды, а удаления
  пользователя и ноды уносят их часть трафика; отдельная проверка — socks5: панель создаёт
  ноду через прокси (`host:port` без схемы понимается так же), masked-форма не несёт пароль,
  целый прокси отдаёт только `GET /api/nodes/{id}/proxy`, чужая схема (http/https) отвергается
  человеческим текстом, а в живой связке проверка поднимает настоящий socks5-сервер
  (`tools/socks5.py`): поход до ноды проходит через него (журнал `connections` это видит),
  применение конфига идёт тем же путём, при отказе прокси виноватым назван прокси, а не нода,
  снятый прокси возвращает панель на прямой ход;
* `tools/xray_test.py` — рендер конфига и применение к ноде (подняты **две** тестовые ноды:
  хоп обязан доехать до своей): инбаунды vless (plain/reality/
  ws/grpc), vmess, trojan (tls и reality) и shadowsocks с `users`, теги инбаундов = имена
  хостов, ключи подписчика, отпечаток конфига (`config_hash`), две шкалы ревизий и то, что
  неподнявшийся конфиг не меняет рабочий; hy2, ss+tls, vmess+reality и ss+ws отвергаются
  слоем выше (панель не создаёт хост, который Xray не поднимет); отдельно — хопа цепочки на
  двух нодах (пароль и uuid перехода совпадают с инбаундом следующего хопа, маршрут по
  inboundTag, удаление цепочки сняло инбаунды и переходы на обеих нодах) и криптография
  tls-хопа: отпечаток PEM-сертификата, который нода получила от панели, равен
  `pinnedPeerCertSha256` в конфиге отправляющей ноды, и сертификат назван адресом хопа, если
  человек его назвал (переход соседней ноды идёт на тот же адрес, а hop без своего адреса —
  на адрес своей ноды) и настройки самого хопа: `ws path`/`hostHeader`, `serviceName`,
  `sni` (он же CN выданного сертификата, названный отдельно от адреса хопа),
  `rejectUnknownSni`, `fp` и `dest`/`serverNames` reality-хопа — всё это и в его инбаунде,
  и в переходе соседней ноды: обе стороны перехода собраны из одной строки хопа; и трафик: конфиг со счётчиками проходит
  `xray -test`, сервис счётчиков слушает только петлюбочный адрес и не наступил на порты хостов
  (панель писала туда 0, порт подобрала нода), для его ответов есть отдельный `blackhole` и
  правило маршрута, метки настоящие, а путь «Xray насчитал → нода скопила → панель разложила по
  людям» сходится до байта (и цифры ноды, и цифры панели — одни и те же);
* `tools/live_demo.py` — единственный прогон с настоящими бинарниками: девять хостов и два
  подписчика, автоприменение конфига, туннель каждого протокола через SOCKS с конфигом из
  ссылок самой подписки (`generate_204` наружу) и вся подписка через Mihomo — YAML принят,
  группа переключается, трафик идёт (reality в clash-фазе проверяется как конфиг, его
  туннель берёт на себя Xray-клиент: см. «Что пока не сделано»); и настоящий учёт трафика:
  цифры ноды и цифры панели совпадают, каждый подписчик опознан по своей метке, трафика у людей
  не больше, чем у нод (разница — транзит цепочек), сервис счётчиков слушает петлюбочный адрес
  и не наступил на порты хостов, повторная проверка без нового трафика ничего не удваивает;
  одному hopу назван свой адрес («localhost» вместо 127.0.0.1): переход первой ноды идёт на него,
  сертификат хопа выпущен на это же имя, и туннель цепочки по этому адресу работает (HTTP 204);
  у другого входа названы путь и Host-заголовок websocket-хопа, у tls-хопа — его собственный sni
  (сертификат выпущен на него, переход называет его же в SNI, приёмник чужой SNI отвергает),
  у reality-хопа — его маска и принимаемые имена: всё это доезжает до обеих сторон перехода и до
  ссылки подписчика, и туннель цепочки работает именно на этих настройках;
  именно этот прогон и поймал дыру «счётчики теряются при перезапуске Xray» — после него нода
  обязана снимать их перед всякой остановкой процесса;
* `tools/panel_test.py` заодно держит цепочки (в humans-формулировках: скрытые хопа занимают
  порты, инбаунд и переход собраны правильно, закрепление tls-хопа на месте, правка
  пересобирает хопа и освобождает старые порты, удаление чистит конфиги). Ключи хопов
  сверяются по `collect()` — по тому же словарю, что уезжает ноде, а не по замаскированному
  показу; отдельная проверка: «прежняя база поверх новой панели» (у старой цепочки был один
  хост входа — миграция обязана дорисовать хопа, выдать им ключи и сертификат, занять их
  порты и пометить ноды грязными), «прежняя цепочка заняла API-порт соседней ноды на той же
  машине» (миграция обязана убрать хопа на свободный порт, записать его и в `chains.hops`, и
  сказать об этом человеку; порты обычных хостов она не трогает) и «окно конфига ноды не
  показывает ни ключи, ни пароли переходов»; отдельно занятость портов по машине: хост не может
  занять API-порт соседней ноды, хоп цепочки — тоже, два хопа одной цепочки на одной машине не
  могут взять один порт, API-порт ноды не наступает на порт хоста своей же машины, а переезд
  ноды на чужую машину проверяется по её хостам; и адрес хопа (он сохраняется в цепочке,
  попадает в строку hosts входа и в outbound соседней ноды); и формат подписки: ссылки vmess (base64 JSON), trojan,
  ss с паролем этого хоста, YAML со всеми протоколами и группой выбора, QR ss-хоста и
  reality-ссылку, называющую сайт-маску;
* `tools/ui_test.mjs` — фронт против живого API (без мока): отдельно проверяется правка
  цепочки из интерфейса: окно хопов открывается предзаполненным её же хопами (заголовок
  «изменение», кнопка «Сохранить»), перестановка хопов на те же порты своих же нод не
  считается «портом занят», PATCH сохраняет хопа, а бэкенд в ответ меняет инбаунды нод
  (вход цепочки переезжает на другую ноду, у прежней остаётся только переход), и в списке
  хостов цепочка по-прежнему один хост — её вход, промежуточные хопа не показываются; там же
  настройки самого хопа: ряд хопа показывает поля только своей защиты и своего транспорта
  (reality — маска и принимаемые имена, ws+tls — путь, Host, sni и отказ от чужого SNI; чужих
  полей и файлов сертификата ряд не показывает), сохранённое бэкенд отдаёт обратно, бэкенд
  пересобирает и инбаунд хопа, и переход соседней ноды на тот же путь и тот же sni, а окно
  правки предзаполняет детали каждого хопа;
  создаёт ноды (без API-ключа добавить нельзя), кликает по карточке, проверяет связь с живой нодой и то, что карточка
  не показывает API-ключ, сообщения об ошибках от бэкенда, сохранение настроек через
  перезагрузку и каскадные удаления. Отдельная проверка — «статус обновляется сам»: ноду
  никто не трогает из панели, но она перезапускается с другим API-ключом — и карточка
  сама становится «Недоступна», без кнопки и без перезагрузки страницы; отдельно интерфейс
  цепочек: окно правки предзаполняется хопами вместе с их адресами, карточка цепочки показывает
  адрес хопа, который назвал человек, в окне ноды есть строка «Трафик ноды», а на карточке ноды
  — красная строка с причиной, если её Xray умер; и socks5: тест поднимает настоящий
  socks5-сервер (`tools/socks5.py` как процесс), вписывает его прокси в окно ноды, reopening
  окна получает поле предзаполненным целиком (`openNodeEdit` читает `/api/nodes/<id>/proxy`;

  что нода ответила через прокси и отвергла не тот ключ (то есть дорога работала), а когда
  прокси убивают — та же кнопка винит прокси, а не ноду; в списке нод пароля прокси нет;
